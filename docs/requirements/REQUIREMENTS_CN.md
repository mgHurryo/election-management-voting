## 1. 项目简介 / Introduction

### 1.1 目的 / Purpose

本文档把 Kickoff 会议（Meeting 01，2026-09-25）已达成的结论正式化为一份结构化需求规格，作为后续接口设计、开发分工和测试验证的共同依据。

按课程「需求工程」的要求，一份好的需求文档应做到 **完整（complete）** 与 **一致（consistent）**：该有的功能都写清楚，且前后不自相矛盾。

v0.1 是一份**只含已拍板内容**的基线：凡是会议尚未确定的规则或指标，一律不作为本版需求，统一推迟到 [Future Work](../future/FUTURE_CN.md)，以免开发把「待确认」误当成「必须做」。

### 1.2 项目概述 / Project Overview

本项目开发一个**选举管理与投票系统**，用于支持校园组织（如班级、学生会）进行简单、可运行、可测试的选举与投票活动。

MVP 系统主要面向**选举管理员**和**选民**：管理员创建并配置选举、维护候选人与选民名单；合资格选民登录后完成投票；投票结束后，系统负责计票并公布结果。

本项目首先实现一个**最小可运行 MVP**，目标不是支持所有复杂的选举制度，而是先把一条能跑通、能演示、能验证的核心链路做扎实：

```text
配置选举 → 管理候选人与选民 → 身份认证与投票资格校验 → 投票 → 计票与发布结果
```

### 1.3 Demo 场景基线

本版 MVP 锁定一个**明确、普通、容易验证**的场景作为交付基线（详见第 2 节）：

> **班长选举**——本班班长因病休学，需要在班中选举一位新班长；单选、一人一票、得票最高者当选。

MVP 中，**一场选举只选出一个职位（班长）**。一场选举同时选多个职位（如主席、副主席、秘书）属于 Future Work（FW-02）。

选择单一场景的目的，是让需求边界清晰、可测试；其他选举制度作为 MVP 之后的扩展（详见 [Future Work](../future/FUTURE_CN.md)）。

### 1.4 版本项目范围（MVP）

这个版本为本项目中最小可运行 Demo，旨在进行原型实现与验证。首版 MVP 覆盖以下能力（主要对应模块 M1–M7；M8 审计日志列入 Future Work）：

- 选举配置（M3）
- 候选人管理（M3）
- 选民名单管理（M2）
- 身份认证（M1）
- 角色与基本权限控制（M1）
- 投票资格检查（M2 / M4）
- 投票提交（M4）
- 投票次数限制 / 一人一票（M4）
- 选票匿名存储（M5）
- 计票（M6）
- 结果发布（M7）

注意，MVP 范围**不包含**以下内容（完整清单见 [Future Work](../future/FUTURE_CN.md)）：

- 区块链存证
- 移动原生 App
- 真实选民数据库接入
- 复杂多轮选举
- 复杂权重机制
- 复杂平票及晋级机制
- 支持所有选举制度的通用工作流

> **范围纪律**：以后若有人提出「要不要再加 XXX」，先看本节。不在 MVP 范围里的，一律记为 v0.1 不做，进 backlog（[Future Work](../future/FUTURE_CN.md)），不临时扩范围。任何业务改动须先报组长，由组长决定并记入变更记录。

### 1.5 术语约定

| 术语 | 含义 |
| --- | --- |
| 选举（Election） | 一次完整的投票活动，含名称、职位、时间窗、候选人和选民范围 |
| 选民（Voter） | 被列入某场选举名册、具备投票资格的用户 |
| 候选人（Candidate） | 被选举的对象；**在 MVP 中是一个业务实体 / 数据对象，不是系统 Actor，不关联登录账号** |
| 名册（Voter Roll） | 某场选举的合资格选民清单 |
| 选票（Ballot） | 选民针对某职位提交的投票选择 |
| 有效票 | 通过资格校验、在规定时间窗内、未超次数限制而成功保存的选票 |

## 2. 系统使用流程 / System Scenario

按课程要求，场景应包含：初始情况、正常事件流程、可能出现的问题、并行活动、以及结束状态。

### Scenario 1：班长选举

**初始情况**
本班班长因病休学，需要选举一位新班长。选举管理员（如辅导员或班委）在系统中创建这场选举。

**正常流程**

1. 管理员创建选举，设置选举名称、要选出的职位（班长）、投票开始与结束时间。
2. 管理员录入候选人信息（姓名、职位、简介、照片），并把本班具备投票资格的学生加入选民名册。
3. 投票开放期间，选民登录系统。
4. 系统验证选民身份，并校验其是否在该场选举的名册内。
5. 验证通过后，选民查看选票，浏览候选人资料，选择一名候选人。
6. 系统再次校验身份、资格与投票次数，接受这张选票，并阻止超额、无资格或非法的投票。
7. 投票结束后，管理员关闭选举。
8. 系统完成计票，管理员发布最终结果；得票最高者当选班长。

**可能出现的问题**

- 用户已登录但不在本场名册内 → 系统拒绝进入投票并提示无资格。
- 选民已投过一次仍尝试再投 → 系统拒绝，原选票不被修改。
- 在投票开始前或结束后尝试投票 → 系统拒绝。
- 出现平票 → v0.1 不处理（见 BR-08 与 FW-10）。

**并行活动**
多名选民可同时在线投票，互不可见彼此的投票内容；管理员不得查看或修改任何已投出的选票内容。

**结束状态**
选举关闭、计票完成、结果发布；结果对获授权的用户可见，且计票数字与系统中保存的有效选票一致。

## 3. 用户角色 / Actors

MVP 中，角色缩减到 **3** 个；其中真正登录并操作系统的只有管理员与选民。

### 3.1 Administrator 管理员

```text
可以：
- 创建选举
- 配置选举
- 管理候选人
- 管理选民
- 开启/关闭投票
- 查看和发布结果

不能：
- 修改或删除已经投出的选票
- 查看某张选票具体投给了谁（匿名性，见 NFR-2）
```

### 3.2 Voter 选民

```text
可以：
- 登录
- 参与合资格选举
- 查看自己的选票
- 投票
- 查看公开结果

不能：
- 看到别人投给了谁
- 投出后修改自己的选票
- 超过规定的投票次数
```

### 3.3 Candidate 候选人（业务实体，非系统 Actor）

在 MVP 中，候选人是一个**业务实体 / 数据对象，而不是系统 Actor**。候选人不关联登录账号，由管理员负责维护其资料。
大白话：候选人不需要登录系统，它只是被系统管理和展示的数据。

> 重要原则：**Actor ≠ 数据库里出现的实体。** 只有会登录并触发系统行为的主体才作为 Actor 建模；候选人是实体（Entity），不是 Actor。

### 3.4 会议提到但 MVP 不单独建模的角色

会议画面曾列出六种系统角色（选民、候选人、选举管理员、审计员、系统管理员、选举委员会）。为控制 MVP 范围：

- **审计员 / 选举委员会**：其职责（复核计票、验收结果）在 MVP 中由管理员承担，不单设账号与权限。
- **系统管理员**：账号与运行环境维护在 MVP 中由开发/部署流程处理，不作为业务 Actor。

这些角色的独立化列入 backlog（FW-06）。

## 4. 功能需求 / Functional Requirements

每条只描述一件事，均可被测试。v0.1 只写已拍板的需求；未确定的一律不写进本节，改列入 [Future Work](../future/FUTURE_CN.md)。

### FR-01 创建选举（M3）

```text
系统应允许管理员创建一个新的选举。
创建时管理员至少需提供：
- 选举名称 / 主题
- 要选出的职位（MVP：单场选举一个职位）
- 投票开始时间
- 投票结束时间
- 合资格投票人范围
系统应保存该选举信息，并允许重新查询。
```

> MVP 仅以「投票结束时间」作为结束条件；其他结束条件（如达到结束票数即自动关闭）见 FW-12。

### FR-02 配置选举（M3）

```text
系统应允许管理员在投票开始前配置选举的票制。
MVP 支持的票制为：单选、一人一票、得票最高者当选。
```

### FR-03 管理候选人（M3）

```text
系统应允许管理员向指定选举添加、修改或删除候选人。
每个候选人至少包含：
- 姓名
- 所竞选职位（title）
- 基本介绍
- 照片（可选）
管理员仅可在投票开始前修改或删除候选人。
```

### FR-04 管理选民名册（M2）

```text
系统应允许管理员维护某场选举的合资格选民名册。
只有存在于有效名册中的用户，才具备该场选举的投票资格。
系统应支持名册去重。
```

### FR-05 身份认证（M1）

```text
系统应要求用户登录后才能进入投票或管理流程。
身份认证失败时，系统不得允许用户进入任何受保护功能。
```

### FR-06 角色与访问控制（M1）

```text
系统应根据用户角色（管理员 / 选民）限制其可执行的操作。
无相应权限的用户不得访问管理员功能或他人数据。
```

### FR-07 投票资格校验（M2 / M4）

```text
系统应在展示选票前和提交选票前，校验用户是否具备该场选举的投票资格。
不具备资格的用户不得查看选票，也不得提交选票。
```

### FR-08 查看选票（M4）

```text
具备资格的选民可在投票开放期间查看选票。
选票应显示当前选举对应的职位与候选人及其资料。
```

### FR-09 提交投票（M4）

```text
具备资格的选民可在投票开放期间提交选票。
系统应保存通过全部校验的有效匿名选票，并返回投票成功结果。
候选人得票数由计票过程（FR-12）根据有效选票计算得出；
投票阶段只保存选票，不直接修改或累加任何计票结果。
```

### FR-10 一人一票限制（M4）

```text
系统应限制每位选民在单场选举中的投票次数（MVP：最多一次）。
当用户已达到允许的投票次数时，系统必须拒绝新的投票请求，
且不得修改其已投出的选票。
```

### FR-11 选票匿名存储（M5）

```text
系统应保存有效选票，并保证选票内容与其投票人身份分离存储。
系统不得提供从某张选票反查投票人的能力。
```

### FR-12 计票（M6）

```text
系统应能统计每个候选人获得的有效票数。
计票结果必须与系统中保存的有效选票完全一致。
系统应支持结果复核（复算得到相同结果）。
```

### FR-13 开启 / 关闭投票（M3）

```text
系统应仅允许管理员开启或关闭某场选举的投票。
管理员的状态控制不得突破设定的投票时间窗（见 BR-11、BR-12）。
选举关闭后，系统不得再接受任何新的选票。
```

### FR-14 发布结果（M7）

```text
选举结束后，管理员可发布选举结果。
结果至少显示：
- 各候选人及其得票数
- 投票率（可选）
- 最终当选者
```

> MVP 中结果发布后对获授权用户（管理员与选民）可见；更细的分角色可见性策略见 FW-13。

## 5. 非功能需求 / Non-Functional Requirements

按课程分类：**产品需求**（产品应如何运行）、**组织需求**（来自团队/课程流程）、**外部需求**（法律、互操作等）。非功能需求应尽量可量化；v0.1 暂无法量化的，明确推迟到 Future Work，不写成模糊承诺。

### NFR-1 安全性（产品）

- 所有用户输入、请求与外部数据均视为不可信，须做参数校验与权限校验。
- 认证、访问控制与投票资格校验须防止刷票、越权投票和跨选举访问。
- 凭据、密码等敏感信息不得明文存储或写入日志。

### NFR-2 匿名性与隐私（产品，关键）

- 选票内容必须与投票人身份**分开存储**；匿名性靠数据模型设计保证，而非事后加密补救。
- 一旦选票存储指向具体选民，后续无论怎样加密都无法恢复匿名性——因此该约束必须在设计阶段落实。
- 任何角色都不得由某张选票反推出投票人。
- **一人一票与匿名性如何共存**：系统可以记录某选民「是否已完成投票」这一状态，用于执行一人一票限制；但该状态不得包含、关联或推导出该选民具体提交的选票内容。

```text
可以保存：  张三 → 已投票        ✅
不得保存：  张三 → 投给了李四    ❌
```

### NFR-3 可靠性与数据一致性（产品）

- 不得丢票、重复计票或错计；计票结果须与有效选票一致。
- 提交投票等副作用操作须考虑并发与幂等，避免同一选民产生多张有效票。

### NFR-4 性能与规模（产品）

- MVP 面向班级 / 小型校园组织级选举。
- **v0.1 不设量化性能验收门槛**；并发用户数、投票提交与计票的响应时间等量化指标，待技术验证后在未来版本定义（见 FW-11）。

### NFR-5 易用性（产品）

- 选民从登录到完成投票的路径应简单清晰，关键错误（无资格、已投票、未开放）应给出可理解的提示。

### NFR-6 技术约束（组织）

- 技术栈已定：前端 **React**，后端 **Python FastAPI**，数据库 **MySQL**。
- 该约束来自会议决策，作为组织级约束记录；具体实现细节不在本文档展开。

### NFR-7 可测试性与交付（组织）

- **Kickoff 会议已确认**：所有成员完成各自功能后共同参与验证；条件允许时补充自动化测试。需求与接口文档是开发依据，接口须明确用途、参数与返回，避免前后端各自定义不一致。
- **会后由组长正式追加的项目规则**（非 Kickoff 已确认需求）：采用测试先行，每位成员先为自己负责的模块编写测试用例；PR 合并前 CI 必须全绿。

### NFR-8 时间与交付约束（组织）

- 项目周期约六周；首个可演示 Demo 目标两周内完成，最迟不超过四周。
- 若时间不足，优先交付稳定的基础版本；扩展功能另开分支，形成「基础版 + 扩展版」两个版本。

### NFR-9 外部约束

- MVP 不对接真实选民数据库，使用系统内维护的名册数据。
- 不引入区块链存证，不提供移动原生 App。

## 6. 业务规则 / Business Rules

功能需求描述「系统能做什么」，业务规则描述「系统做事时必须遵守的规矩」。

```text
BR-01  只有具备对应选举投票资格（在有效名册内）的用户才能投票。
BR-02  用户只能在投票开放时间内提交选票。
BR-03  用户在该场选举中不得超过规定的最大投票次数（MVP：一次）。
BR-04  选举关闭后不得再提交新的选票。
BR-05  只有管理员能够创建或修改选举、候选人与名册。
BR-06  只有管理员能够开启/关闭投票与发布最终结果。
BR-07  班长选举中，每位选民最多选择一名候选人（单选）。
BR-08  得票最高者当选；v0.1 不处理平票（平票处理方式见 FW-10）。
BR-09  选票一经投出即不可修改、不可撤回、不可被任何人删除。
BR-10  任何角色都不得将选票与投票人身份关联或反查；系统可记录「某选民是否已投票」
       以执行一人一票，但该状态不得关联其选票内容。
BR-11  只有当选举状态为 OPEN，且当前时间位于投票开始时间与结束时间之间时，
       系统才接受选票。时间窗决定投票是否合法。
BR-12  管理员负责选举的状态控制（开启/关闭），但不得突破时间窗：
       不得在设定的开始时间之前开放投票，也不得在结束时间之后重新开放投票；
       管理员可以提前关闭选举。
```

> 说明：多选、权重、平票处理、多轮晋级等规则均属 MVP 之后（见 [Future Work](../future/FUTURE_CN.md)）。当前只把「单选 + 一人一票 + 得票最高者当选」这条最小规则写死，其余保持可配置空间但不实现。

## 7. 验收标准 / Acceptance Criteria

需求必须能测试。以下用 Given / When / Then 描述 MVP 的关键验收点，全组据此验证。

### AC-01 创建选举

```text
Given 管理员已登录
When  管理员填写合法的选举名称、职位、开始与结束时间并提交
Then  系统成功创建选举，并能重新查询到该选举
```

### AC-02 合资格选民成功投票

```text
Given 选民已登录、在本场名册内、投票处于开放期、且尚未投过票
When  选民查看选票、选择一名候选人并提交
Then  系统保存这张有效选票，并提示投票成功
```

### AC-03 无资格用户投票被拒

```text
Given 用户已登录，但不在本场选举名册中
When  用户尝试进入投票页面或提交选票
Then  系统拒绝，并返回「无投票资格」的提示
```

### AC-04 重复投票被拒

```text
Given 选民已完成一次投票，且本场最多只能投一次
When  选民再次提交选票
Then  系统必须拒绝该请求，且原选票不得被修改
```

### AC-05 时间窗外投票被拒

```text
Given 选举尚未开始或已关闭
When  合资格选民尝试提交选票
Then  系统拒绝，并返回相应的未开放/已结束提示
```

### AC-06 计票与发布结果

```text
Given 选举已关闭且存在若干有效选票
When  管理员触发计票并发布结果
Then  各候选人得票数与系统保存的有效选票一致，得票最高者显示为当选
```

### AC-07 匿名性

```text
Given 存在已保存的有效选票
When  任意角色（含管理员）查询系统数据
Then  无法从任何一张选票反查出投票人身份
```

### AC-08 状态控制不得突破时间窗

```text
Given 选举设定的开始时间为 T_start、结束时间为 T_end
When  管理员在 T_start 之前尝试开启投票，或在 T_end 之后尝试重新开启投票
Then  系统拒绝该操作；仅当状态为 OPEN 且当前时间在 [T_start, T_end] 内时才接受选票
```
